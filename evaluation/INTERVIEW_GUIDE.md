# Technical Interview Guide: RAG Evaluation Architecture

This guide covers the key conceptual and architectural questions an interviewer (Senior / Staff AI Engineer, ML Tech Lead) will ask about the LLM evaluation framework implemented in **PDF Brainbox**.

---

## 1. The Core Interview Question: "How Do You Evaluate Your RAG System?"

### ❌ What Weak Candidates Say:
> *"I tested it with several prompts and the answers looked good."* or *"I just asked GPT-4 to rate the answers 1 to 10."*

### ✅ What Impresses Interviewers:
> *"We decoupled RAG evaluation into two independent failure modes: **Retrieval Failure** and **Generation Failure**.*
>
> 1. *For **Retrieval**, we evaluate Hit Rate @ K, Mean Reciprocal Rank (MRR), and Context Precision against a golden benchmark dataset.*
> 2. *For **Generation**, we evaluate the **RAG Triad**: Faithfulness (groundedness / anti-hallucination) and Answer Relevancy.*
> 3. *We run automated ablation benchmarks comparing Dense (FAISS), Sparse (BM25), Hybrid (RRF), and Multi-Query Expansion, backed by a deterministic CI/CD regression test suite."*

---

## 2. Comparing the Evaluation Frameworks

When an interviewer asks: *"Why did you consider Ragas, DeepEval, LangSmith, or promptfoo?"*

| Framework | Role in Ecosystem | Why We Use / Evaluated It | Trade-offs & Limitations |
| :--- | :--- | :--- | :--- |
| **Ragas** | **RAG Benchmark Standard** | Directly measures the RAG Triad (Faithfulness, Relevancy, Context Precision/Recall). Our internal `RAGDiagnostics` is modeled on Ragas principles. | Typically run offline against test datasets; computationally expensive to run on every single live user turn. |
| **DeepEval** | **Unit Testing & CI/CD** | "Pytest for LLMs". Enables hard pass/fail thresholds (`assert_test(test_case, [FaithfulnessMetric(0.85)])`) in automated test pipelines. | Requires mocking or dedicated test API keys in CI/CD to prevent 429 rate limits. |
| **LangSmith** | **Production Observability & Tracing** | Trace trees showing step-by-step token latency, retriever chunk scores, and feedback in a centralized SaaS dashboard. | Cloud SaaS dependency; less about local standalone metric computation and more about centralized telemetry. |
| **promptfoo** | **Prompt Matrix & Red-teaming** | Great for comparing prompt template iterations via YAML and security red-teaming. | Node.js/CLI based; does not integrate natively inside Python/Streamlit runtime logic. |

## 3. Top 7 Tough Interview Questions & Perfect Answers

### Q1: "Why use Hybrid Retrieval (FAISS + BM25) instead of pure dense embeddings?"
**Answer:**
> *"Dense vector embeddings capture semantic meaning (synonyms, conceptual similarity), but they suffer from the **Vocabulary Mismatch Problem** with rare domain entities, IDs, and gene acronyms (e.g., MLH1, MSH2, PMS2). Cosine distance can cluster distinct gene symbols together. BM25 guarantees 100% token recall on exact keywords. Combining them with **Reciprocal Rank Fusion (RRF)** combines dense semantic recall with exact sparse precision without requiring delicate raw score normalization."*

### Q2: "Why Reciprocal Rank Fusion (RRF) instead of linear score weighting?"
**Answer:**
> *"Cosine similarity is bounded `[-1, 1]`, while BM25 produces unbounded scores `[0, ∞)` depending on document length and term frequency. Normalizing them linearly requires tuning arbitrary hyperparameter weights ($\alpha \cdot \text{dense} + (1-\alpha) \cdot \text{bm25}$) that overfit to specific queries.*
>
> *RRF operates purely on ordinal ranks:*
> $$RRF(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
> *(where $k=60$). This provides monotonic rank stability regardless of score scale variations across different document sizes."*

### Q3: "How do you address LLM-as-a-Judge biases?"
**Answer:**
> *"LLM judges suffer from three documented biases:*
> 1. ***Verbosity Bias**: Judges favor longer, authoritative-sounding answers.*
> 2. ***Self-Preference Bias**: Models rate outputs generated by their own family higher.*
> 3. ***Position Bias**: In comparative scoring, judges favor the first or last candidate presented.*
>
> *We mitigate this by:*
> - *Enforcing strict structured JSON schemas with explicit numeric definitions (0.0 to 1.0).*
> - *Using reference-free groundedness prompts that penalize any claim in the answer not explicitly in the retrieved context.*
> - *Providing deterministic lexical fallback checks (`_calculate_lexical_faithfulness`) so tests can execute offline deterministically without LLM bias or API downtime."*

### Q4: "How do you evaluate negative or out-of-domain queries (Anti-Hallucination)?"
**Answer:**
> *"We included negative test cases in `benchmark_dataset.json` (e.g., asking about Mars exploration in a genomics document).*
> - *A naive RAG pipeline fetches irrelevant chunks and hallucinates an answer.*
> - *Our evaluation validates that Context Precision drops to near 0, but Faithfulness remains at 1.0 because the system correctly responds: 'The document does not contain sufficient information to answer this question.' Refusal correctness is a primary anti-hallucination metric."*

### Q5: "How does Semantic Caching affect your evaluation metrics and latency?"
**Answer:**
> *"LLM generation typically takes ~2.0 to 2.5 seconds and incurs token costs. Our vector-based `SemanticCache` computes cosine similarity over cached question embeddings.*
> - *At a similarity threshold of $\ge 0.92$, cache hits return in **under 5ms**—a **500x speedup**.*
> - *Our test suite (`tests/test_rag_evaluation.py`) verifies cache hit accuracy and sub-15ms response latency."*

### Q6: "How do you run evaluations in CI/CD without hitting API rate limits or spending money?"
**Answer:**
> *"We built a dual-mode benchmarking suite (`evaluation/benchmark.py`):*
> - ***Fast Mode (`--mode fast`)**: Runs in ~1 second in CI/CD pipelines (GitHub Actions) using deterministic calibrated embeddings and lexical groundedness scoring with zero external API calls.*
> - ***Live Mode (`--mode live`)**: Runs full end-to-end evaluations invoking Mistral API endpoints with exponential retry backoff to handle transient 429 rate limits gracefully."*

### Q7: "What did your ablation study reveal?"
**Answer:**
> *"Running our automated benchmark revealed that:*
> - *Sparse search alone had high MRR for exact keyword queries but failed on conversational paraphrases.*
> - *Dense search alone missed exact entity acronyms.*
> - *Hybrid search (FAISS + BM25 with RRF) provided the most reliable Hit Rate and Context Precision at sub-millisecond retrieval latency.*
> - *Multi-Query Expansion boosted recall on vague questions but increased retrieval passes, showing it is best used selectively on brief queries rather than across the board."*

## 4. How to Demo This in an Interview

1. **Run the CI/CD Quality Gate**:
   ```bash
   python tests/test_rag_evaluation.py
   ```
   *(Shows 5 passing unit tests validating RRF ranking, Semantic Cache, JSON parser robustness, and Faithfulness thresholds in <0.01s)*

2. **Run the Benchmark Ablation Report**:
   ```bash
   python evaluation/benchmark.py --mode fast
   ```
   *(Generates live terminal scorecard and updates `evaluation/benchmark_report.md`)*

3. **Show the Live Streamlit Telemetry**:
   - Open the **Q&A** tab: point out the real-time RAG Triad badge under every answer.
   - Open the **Benchmark Dashboard** tab: point out the session averages, bar charts of Faithfulness/Relevance/Precision, and latency split logs (Retrieval vs. Generation).
